# Brief: bulk-mark-read

出典: [Issue #5 複数記事を一括で既読にする機能を追加する](https://github.com/okotaro/oksskolten/issues/5)

## Problem

未読記事のタイトルを一覧で上から順に確認していき、途中で確認を止めたい場面がある。このとき「ここまで見た分」をまとめて既読にする手段がない。現状は記事を1件ずつ開くか、スクロールによる自動既読に任せるか、フィード全体を既読にするしかない。前者は手間が大きく、後者は未確認の記事まで既読にしてしまう。結果として未読件数が実態と合わなくなり、未読バッジが判断材料として機能しなくなる。

## Current State

既読状態は `articles.seen_at` で管理されている。既存のAPIは次の3種類。

- `PATCH /api/articles/:id/seen` — 単一記事の既読/未読切り替え
- `POST /api/articles/batch-seen` — クライアントが列挙したID配列を一括既読
- `POST /api/feeds/:id/mark-all-seen` — フィード内の全未読を既読

不足しているのは「一覧上の特定の位置を基準にした範囲指定」である。`batch-seen` はID配列を受け取るが、クライアントは無限スクロールで読み込み済みの記事しか把握していないため、絞り込み条件に一致する全件を対象にできない。

UI面では、フィード側に `FeedContextMenu`(Radix ContextMenu)という右クリックメニューの実装パターンが既にあるが、記事カードには右クリックメニューが存在しない。

一覧の並び順はフィルタによって変わる。通常の記事一覧は `published_at DESC`、お気に入り一覧は `liked_at DESC`、既読一覧は `read_at DESC` である。さらに未読・お気に入り・いいね・既読のいずれのフィルタも掛かっていない通常一覧には smart floor という表示範囲の下限が適用される。「上/下」をサーバー側で再現するには、この並び順と表示範囲を一覧と揃える必要がある。

## Desired Outcome

記事一覧で任意の記事を右クリックすると、その記事を基準に「これより上(新しい)を既読にする」「これより下(古い)を既読にする」を選べる。対象は画面に読み込み済みの記事に限らず、現在の絞り込み条件に一致する全件。実行後はトーストで件数が示され、取り消しができる。

## Approach

**方式A: 基準記事＋方向をサーバー側で解決する。**

新しいエンドポイントに、基準記事のID、方向(newer/older)、および一覧が使用しているフィルタ条件を渡す。サーバーは `getArticles` と同じ条件式を組み立て、そのフィルタで有効な並び替え列を基準記事の値と比較して該当行を一括更新する。更新前に対象IDを収集して返し、クライアントは取り消し操作のために保持する。

検討した代替案:

- **published_at のみで比較する案** — SQLは単純だが、お気に入り一覧や既読一覧では並び順と比較基準がずれ、画面上「下」に見える記事が対象から外れる。smart floor も無視するため画面外の古い記事まで既読になる。一括既読は取り返しの付きにくい操作であり、見た目と結果のずれは機能への信頼を損なうため不採用。
- **クライアントが対象IDを列挙して既存の batch-seen に渡す案** — 実装は最小だが、読み込み済みの記事しか対象にできず「現在の絞り込み全件」という要件を満たせないため不採用。

呼び出しUIは右クリックメニューのみとする。既存の `FeedContextMenu` と同じ Radix ContextMenu パターンを記事カードに適用する。

誤操作対策はトースト＋取り消しとする。実行前の確認ダイアログは日常操作を重くするため採用しない。

新規の依存ライブラリは不要。Radix の context-menu、dropdown-menu、および sonner はいずれも導入済み。

## Scope

- **In**:
  - 基準記事と方向から対象記事を解決し一括既読にするサーバーAPI
  - 一括既読を取り消す(未読に戻す)サーバーAPI
  - `getArticles` からフィルタ条件生成部分を切り出し、新APIと共有する
  - 記事カードの右クリックメニュー(Radix ContextMenu)
  - トーストによる件数表示と取り消し操作
  - 未読バッジおよび一覧のSWRキャッシュ再検証
  - i18n 文言(日本語/英語)
  - サーバー・クライアント双方のテスト

- **Out**:
  - メニューアイコンによる呼び出し(タッチ端末対応を含む)
  - キーボードショートカットからの一括既読
  - 一括での未読化・ブックマーク・いいね・削除といった既読以外の一括操作
  - 複数記事のチェックボックス選択UI
  - 既存のスクロール自動既読の挙動変更

## Boundary Candidates

- **対象記事の解決ロジック** — フィルタ条件と並び順から、基準記事より新しい/古い記事のIDを決める責務。サーバーDB層。
- **一括既読の適用と取り消し** — 解決されたID群に対する状態更新、検索インデックス同期、スコア再計算の責務。
- **一覧フィルタ条件の共有表現** — 一覧取得APIと一括既読APIが同じ絞り込みを指すための条件生成の責務。現在 `getArticles` に内包されている。
- **記事カードのメニュー提示** — 右クリックで操作項目を出す責務。UI層。
- **実行結果の通知と取り消し** — トースト表示、取り消し呼び出し、キャッシュ再検証の責務。

## Out of Boundary

- 既読状態そのもののデータモデル変更(`seen_at` / `read_at` の意味は既存のまま)
- smart floor の算出ロジックの変更
- 検索インデックス同期の仕組み自体の変更
- 記事一覧の並び順オプションの追加

## Upstream / Downstream

- **Upstream**: `getArticles` のフィルタ・並び順・smart floor ロジック、`markArticlesSeen` および `markAllSeenByFeed` の更新と検索同期パターン、`FeedContextMenu` のメニュー実装パターン、`useSWRInfinite` による一覧キャッシュ、sonner のトースト基盤
- **Downstream**: 記事カードの右クリックメニューは、今後の記事単位の操作(未読化、ブックマーク、削除など)を載せる土台になる。切り出したフィルタ条件生成は、範囲を指定する他の一括操作からも再利用できる。

## Existing Spec Touchpoints

- **Extends**: なし(本プロジェクト初の spec)
- **Adjacent**: なし。ただし `getArticles` は一覧表示の中核であり、条件生成の切り出しは記事一覧全体に影響する。振る舞いを変えない純粋なリファクタリングに留める必要がある。

## Constraints

- 既存の `getArticles` の挙動を変えないこと。切り出しは内部構造の変更に限る。
- 対象IDは更新前に収集すること。既に既読の記事を取り消し対象に含めてはならない(`markAllSeenByFeed` と同じ方針)。
- 更新後は検索インデックスへ未読状態を同期すること(`syncArticleFiltersToSearch`)。
- 未読に戻す際はスコア再計算と検索同期が必要(`markArticleSeen` の未読化パスと同じ扱い)。
- 対象件数が多い場合でも単一トランザクションで完結させ、SQLite のパラメータ数上限に依存する実装にしないこと。
- サーバーは Fastify + zod によるリクエスト検証、クライアントは React 19 + SWR という既存構成に従う。
- 文言は i18n を経由し、日本語・英語の両方を用意すること。
